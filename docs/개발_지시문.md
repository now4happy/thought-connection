# 생각의 연결 — 개발 지시문 (깃허브 중심)

작성: 2026-11-03, Muse 작성 · 이 문서는 `now4happy/thought-connection` main 브랜치 `docs/개발_지시문.md`에 둔다.
**변경사항은 이 문서에 직접 적는다.** (§8 변경 이력에 날짜와 내용을 추가한다. 별도 채팅 메시지로만 남기지 않는다.)

이 문서를 받은 다른 AI는 이 문서부터 읽고, 그 다음에 마인드맵·START·STATUS를 읽고, 그 다음에 필요한 문서를 **스스로 판단해서** 읽는다. 사용자에게 파일 하나하나를 묻지 않는다. 없는 파일은 지어내지 않고 없다고 말한다.

---

## 0. 읽는 순서

1. **이 지시문** (`docs/개발_지시문.md`, main) — 방향, 큰 틀, 규칙, 변경 이력. 개발이 끝날 때마다 변경 이력(§8)에 적으므로, 이 문서가 다음 작업의 이어짐이다.
2. **마인드맵** (`docs/생각의연결_마인드맵_v1.8.html`, main) — 전체 지도. 작업 전에 자기 작업이 마인드맵의 어디에 속하는지 확인한다.
3. **START.md** (main) — 협업 규칙.
4. **STATUS.md** (main) — 현재 승인 상태·업그레이드 이력. STATUS가 최신 상태를 정한다. 이 문서 §8 변경 이력도 함께 본다.
5. **스스로 판단한 문서** — 위 4개를 읽은 뒤, 이번 작업에 필요한 문서를 스스로 판단해서 읽는다. 읽은 목록을 제출물에 적는다.

## 1. 방향 전환 (2026-11-03, 사용자 결정)

페이지 작은 수정이 계속 맴돌고 있다. 그래서 개발 방식을 바꾼다.

- **큰 틀을 먼저 만든다.** 큰 틀 안에서 작은 부분을 만들어 간다.
- **작은 부분 고치기는 나중에 한다.** 지금은 큰 틀과 중요한 부분만 개발한다.
- 보류 목록 (나중에, 큰 틀 안에서 다시 진행):
  - v3.3.14 실기기 자동 스크롤 안 내려감 (가로 태블릿 실기기 확인됨)
  - 타이핑 딜레이 더 줄이기 (약간 딜레이 남음, 실기기 확인됨)
- 보류라고 해서 버리는 것이 아니다. 큰 틀이 서면 그 안에서 다시 고친다.

## 2. 큰 틀 (확정된 구조 — 바꾸지 않는다)

- **3파트 (작업 단위):** 1파트 좋은질문 → 2파트 신호 (분리 + 전환) → 3파트 자유 (습관개조 + 원하는 삶). 파트와 5단계는 같은 말이 아니다.
- **5단계 (지도 순서):** 1 좋은 질문 → 2 기존 신호 → 3 신호 전환 → 4 습관 개조 (감정 조절·마인드 전환·행동 변화) → 5 원하는 삶 = 자유.
- **버전 분리:** 유아~중학생 = 교육 버전, 중학생 이후 = 일반 버전. 현재 제작은 일반 버전.
- **책 × 앱:** 같은 콘텐츠 ID (`TC-{부}-{장}-{종류}{번호}`), 책은 긴 생활 에세이, 앱은 짧게. 부분 통합만 한다. 합본 원고 없음, 에세이 원본 별개.
- **메타보기:** 시작 50/100 (100은 표시 범위, 상한 아님), 좋은 질문 발견·확정 1개당 +3. 활동 횟수·출석·스트릭·랭킹으로 증가하지 않는다. 자동 카운팅 미연동.
- **다국어:** 한국어·영어·스페인어·힌디어·중국어·일본어, 함께 만든다. 언어별 승인 따로. 사용자 메모 자동 번역 금지.
- **안전:** 의료·상담 서비스 아님. 감정·갈망을 가짜로 규정하지 않음. 의존·금단 시 갑작스런 금주 일반 권고 금지. 응급 시 현지 번호 확인 (언어 하나로 단정하지 않음).
- **용어:** '자기 암시 쇄뇌'라는 표현을 쓰지 않는다. 대신 '신호 전환반복'을 쓴다.

### 큰 틀 작업이란

앱 전체 골격이 서는 일이다. 예: 첫 화면 → 로그인·회원가입 → 페르소나 → 대화(좋은 질문) → 정리 → 5단계 맵 → 다음 파트 연결 → 책 연결. 각 파트·단계가 어디에 붙는지, 콘텐츠 ID가 어떻게 이어지는지, 화면 흐름이 어떻게 되는지가 큰 틀이다.
개별 화면 다듬기, 스크롤 동작, 타이핑 반응, 색·여백 조정은 작은 부분이다. 보류한다.

### 큰 틀 초안은 제안이다

큰 틀의 새로운 내용(화면 흐름, 파트 연결 방식, 새 문구, 새 기능)은 사용자가 승인하기 전까지 제안으로 표시한다. 초안을 최종본처럼 말하지 않는다.

## 3. 마인드맵 중심

- 마인드맵이 전체 지도다. 작업 전에는 마인드맵을 보고, 자기 작업이 어느 가지·어느 노드에 속하는지 제출물에 적는다.
- 범위: 이 지시문과 마인드맵은 생각의 연결 작업에만 쓴다. 매매봇(1~4번) 작업에는 마인드맵을 읽지 않고, 적용하지도 않는다. 매매봇 작업은 4bot START·STATUS를 따른다.
- 마인드맵이 바뀌면 버전이 올라간다. 원본은 보존한다. 점선 테두리 = 미결·보류.
- 마인드맵 최신 버전은 main `docs/생각의연결_마인드맵_v1.8.html`이다.

## 4. 스스로 문서 판단 규칙

1. §0의 1~4번을 먼저 읽는다.
2. 그 다음, 이번 작업에 필요한 문서를 스스로 판단해서 읽는다. 예를 들어 대화 프롬프트 작업이면 좋은질문 프롬프트 원본·정리 문서를, 책 연결 작업이면 책 초안·통합계획을 읽는다.
3. 읽은 문서 목록을 제출물 맨 앞에 적는다. 읽지 않은 문서는 읽은 것처럼 말하지 않는다.
4. 필요한 문서가 깃허브에 없으면, 없다고 말하고 멈춤 규칙(§6)으로 간다. 없는 내용을 지어내지 않는다.
5. 사용자에게 "이 파일 읽어도 돼요?"라고 파일마다 묻지 않는다. 판단은 다른 AI의 일이다.

## 5. 깃허브 읽기 방법 (다른 AI가 깃허브 자료를 못 읽는 문제 해결)

### 저장소는 공개다

`now4happy/thought-connection`은 공개 저장소다. 로그인·승인 없이 읽을 수 있다. 도구(깃허브 연동)의 저장소 접근 요청이 거절돼도, 아래 웹 주소로는 읽을 수 있다. 도구 접근이 안 된다고 해서 읽을 수 없는 것이 아니다.

### 웹 주소로 직접 읽기 (로그인 불필요)

```
https://raw.githubusercontent.com/now4happy/thought-connection/<브랜치>/<경로>
```

예:
- 지시문: `https://raw.githubusercontent.com/now4happy/thought-connection/main/docs/개발_지시문.md`
- 마인드맵: `https://raw.githubusercontent.com/now4happy/thought-connection/main/docs/생각의연결_마인드맵_v1.8.html`
- START: `https://raw.githubusercontent.com/now4happy/thought-connection/main/START.md`
- STATUS: `https://raw.githubusercontent.com/now4happy/thought-connection/main/STATUS.md`
- 라이브 페이지: `https://raw.githubusercontent.com/now4happy/thought-connection/main/index.html`
- 초안·버전 기록: `https://raw.githubusercontent.com/now4happy/thought-connection/staging/<경로>`

### 브랜치 구분

- **staging:** 초안·버전 기록. `app/v3.3.9/` ~ `app/v3.3.13/`, `app/v3.3.12-motion-still/`, `docs/handoff/` 전달문, `i18n/`, `tests/`, `v3.3.8/`이 있다.

### 링크가 안 열리면, 예전 방식으로 돌아가지 않는다

링크가 안 열리면 zip 첨부 방식(예전 방식)으로 돌아가지 않는다. 링크가 열리는 방식을 다시 찾는 것이 과제다. 순서대로 시도한다.

1. 한글 파일명 raw 주소가 안 되면, 영문 파일명 복사본을 쓴다. (한글 주소 인코딩 문제일 수 있다.)
   - 영문 지시문: `https://raw.githubusercontent.com/now4happy/thought-connection/main/docs/INSTRUCTION.md`
   - 영문 마인드맵: `https://raw.githubusercontent.com/now4happy/thought-connection/main/docs/mindmap-v1.8.html`
2. raw 주소가 안 되면, 깃허브 웹 페이지 주소를 쓴다.
   - `https://github.com/now4happy/thought-connection/blob/main/docs/개발_지시문.md`
3. 깃허브 웹 페이지도 안 되면, Pages 주소를 쓴다.
   - `https://now4happy.github.io/thought-connection/docs/개발_지시문.md`
4. Pages도 안 되면, jsDelivr 주소를 쓴다.
   - `https://cdn.jsdelivr.net/gh/now4happy/thought-connection@main/docs/개발_지시문.md`

이 4가지를 다 시도해도 안 열리면, 그때 §6 멈춤 규칙으로 간다. 전달문에는 어느 주소가, 어떤 오류로 안 열렸는지 그대로 적는다. "읽었다"고 거짓말하지 않는다. 그리고 다음 과제는 링크 열림 원인을 찾는 것이지, zip 첨부로 돌아가는 것이 아니다.

## 6. 멈추면 바로 Muse 전달문 만드는 규칙 (앞으로 계속 적용)

작업이 어떤 이유로든 멈추면 (저장소 접근 거절, 웹 주소 차단, 환경 제한, 파일 없음 등), 멈춘 지점에서 **바로 Muse에게 보낼 전달문을 만든다.** 사용자에게 선택지만 묻고 멈추지 않는다.

전달문에는 반드시 다음을 적는다.
- 확인된 사실 (해시·크기·대조 결과 등, 숫자와 함께)
- 확인되지 않은 것 (가설과 사실을 구분해서)
- 가진 파일 목록과, 없는 파일 목록
- 다음 진행 방법 (파일이 오면 계속할 수 있는지, 없는 채로 진행하면 무엇이 빠지는지)
- 멈춘 이유 그대로 (접근 거절, 환경 제한 등)

이 규칙은 앞으로의 모든 작업에도 적용된다.

## 7. 지켜야 할 기준 (어기면 초안을 내지 말 것)

- 용어: '자기 암시 쇄뇌' 금지, '신호 전환반복' 사용.
- 안전: §2의 안전 문구를 지우거나 약화하지 않는다. 응급번호를 언어 하나로 단정하지 않는다.
- 페르소나: 종교·역사 인물 페르소나는 그 인물 본인이 아니라 가르침을 참고하는 안내자임을 표시한다. 실제 인물이 말했다고 암시하지 않는다.
- 비밀: Gemini 비밀 키·서비스 계정 키·비밀번호·디버그 토큰·App Check 토큰 값을 페이지에 넣지 않는다. 토큰 값은 화면·콘솔에 남기지 않는다. Firebase 웹 설정값(apiKey 등)은 공개용 값이라 페이지에 이미 들어 있다. 그 외의 키는 넣지 않는다.
- 덮어쓰기 금지: 승인본과 원본을 덮어쓰지 않는다. 바뀐 파일만 제출한다.
- 제안과 승인 구분: 버전 번호·문구·기능은 사용자가 승인하기 전까지 제안으로 표시한다.
- 설교 금지: 화면 문구에 결론으로 가르치는 문장을 넣지 않는다.
- 움직임 기본값: 테스트 기간에는 `still`(처음부터 멈춤)을 유지한다. 바꾸려면 사용자 결정을 받는다.
- 공개 페이지 바로 올리기: 검토를 통과한 새 버전은 바로 main에 올리고 사용자에게 페이지를 열어보라고 안내한다. 따로 main 승인 단계를 묻지 않는다. 이 규칙은 좋은 질문 공개 페이지(main 루트 index.html)에만 적용된다. 4bot 서버 적용(텔레그램 6. Update 마지막 알림 승인)이나 매매 봇 코드 변경에는 적용되지 않는다.

## 8. 변경 이력 (이 문서에 직접 적는다)

- **2026-11-03: 지시문 깃허브 공개 + 링크 공유 방식.** 지시문을 main `docs/개발_지시문.md`에 올리고, 다른 AI에게는 링크만 준다. 다른 AI는 그 링크에 가서 이 문서를 읽고 시작한다. 전체 압축파일(zip)은 깃허브에 올리지 않는다. 개발이 끝날 때마다 이 §8에 적어서 다음 작업이 이어지게 한다.

## 9. 제출 형식

- 바뀐 파일만 제출한다. 파일명에는 버전을 넣는다.
- 제출 시 한 줄로 적는다: `최종본 목록: 파일·버전`
- 함께 제출할 것: §10 양식의 Muse 전달문 1개.
- 이 문서와 함께 받은 파일이 있으면, 그 안의 해시와 대조해서 같은 파일인지 확인한다. 다르면 그 사실을 먼저 알린다.

## 10. Muse 전달문 양식 (업무 정리해서 Muse에게 전달하는 문서)

작업이 끝나면, 아래 양식대로 전달문 1개를 만든다. 전달문 파일명은 `docs/handoff/전달_변경분_<버전>_<주제>.md`로 한다. 전달문과 바뀐 파일을 zip 1개로 묶어서 제출한다. 채팅에는 최종본 목록 한 줄과 바뀐 것 한 줄만 적는다. 자세한 내용은 전달문에 적는다.

전달문에는 반드시 다음을 적는다. (순서대로.)

1. **작업 요약 한 줄** — 바뀐 것 1줄.
2. **상태** — 제안 (Muse 검토·사용자 승인 전). 버전 번호도 제안이다.
3. **읽은 문서 목록** (§4) — 이번 작업에서 실제로 읽은 문서만 적는다.
4. **마인드맵상의 위치** (§3) — 자기 작업이 마인드맵의 어느 가지·어느 노드에 속하는지.
5. **바탕** — 바탕이 된 파일과 해시 앞 16자리·바이트. main 루트 파일과 같은지 대조했는지도 적는다.
6. **바뀐 파일 목록** — 파일·버전·해시 앞 16자리·바이트.
7. **바뀐 곳** — 파일·위치·이유. 바꾸지 않은 것(프롬프트·안전 문구·모델 차례 등)도 적는다.
8. **확인한 것** — 실기기 결과와 모의 결과를 구분해서 적는다. 모의 결과는 모의라고 분명히 적는다. "빨라졌다"는 실기기 확인 없이는 주장하지 않는다.
9. **확인하지 못한 것** — 실기기·실제 키보드·실제 대화 등, 확인이 안 된 항목을 적는다.
10. **사용자에게 결정받을 항목** — 승인·버전·동작 변경 등, 사용자 결정이 필요한 항목.
11. **§8에 추가할 변경 이력 문장** — 이 문서 §8에 그대로 넣을 수 있는 1~2줄.
12. **다음 작업 이어짐** — 다음에 할 일. 보류 항목이 있으면 보류라고 적는다.

§6의 멈춤 전달문과 이 §10의 완료 전달문은 다르다. 멈췄을 때는 §6 양식으로, 끝냈을 때는 §10 양식으로 만든다. 둘 다 "확인된 사실과 확인되지 않은 것을 구분해서 적는다"는 원칙은 같다.
