## 1. 문제 A — 401 "Firebase App Check token is invalid"

### 1-1. 문서·코드로 확인한 사실

- **App Check 토큰 발급에 실패해도 SDK는 오류를 내지 않는다.** 대신 가짜(dummy) 토큰을 붙여 AI 요청을 그대로 보낸다(SDK `app-check/src/internal-api.ts`, `makeDummyTokenResult`). 서버가 이 가짜 토큰을 받으면 "token is invalid"로 거절한다고 보는 것이 자연스럽다. 다만 서버 응답 문구까지 문서로 확인하지는 못했다.
- 발급 실패가 HTTP 403이나 404이면 SDK는 **하루 동안** 재발급을 막는다(같은 파일 `providers.ts`). 코드 주석에 적힌 403의 원인은 "Attestation failed / Wrong API key / Project deleted"다. 이 차단은 메모리에만 있어서 새로고침하면 풀린다.
- Firebase AI Logic의 App Check에는 **기본 보호(Baseline)**와 별도로 **재사용 방지(Replay protection)** 설정이 있다. 재사용 방지를 적용하면 "일반(session) 토큰 요청은 막힌다." 이때는 앱에서 `getAI(…, {useLimitedUseAppCheckTokens:true})`로 **일회용(limited-use) 토큰**을 보내야 한다. (Firebase AI Logic "App Check" 문서, 2026-10-27 갱신)
- 재사용 방지가 적용되지 않은 상태에서도 **일회용 토큰은 일반 토큰처럼 통과한다**(같은 문서). 일회용 토큰은 5분짜리이고, 요청마다 새로 받아야 해서 "지연과, 공급자에 따라 비용"이 생긴다(같은 문서).
- 2026-11-02부터 AI Logic에 App Check 적용이 필수다. 자동 적용은 2027-01-21까지만 미룰 수 있다(같은 문서). 문서상 자동 적용으로 켜지는 것은 기본 보호다. 재사용 방지는 따로 정하는 설정이다.
- 다른 사람의 공개 저장소 PR 한 건(2026-10-30)에 같은 401을 겪은 사례가 있다. 그 사람은 일반 토큰은 401, 일회용 토큰은 응답을 받았고, `useLimitedUseAppCheckTokens: true`로 해결했다. **참고일 뿐 이 프로젝트에 맞는지는 확인되지 않았다.**
- 페이지에 디버그 토큰(`FIREBASE_APPCHECK_DEBUG_TOKEN`)은 없다. v3.3.11·v3.3.12 모두 0건이다.

### 1-2. 원인 가설 (콘솔 확인 전까지 가설)

| 가설 | 내용 | 맞다면 |
|---|---|---|
| H1 인증 실패 | App Check 앱 등록이 안 됐거나, 공급자·키가 다르거나, 키 도메인에 `now4happy.github.io`가 없거나, 키가 다른 프로젝트에 있거나, 체크박스형 키다 → 토큰 발급 실패 → 가짜 토큰 → 401 | 콘솔 교정이 필요하다(5절 1·3) |
| H2 재사용 방지 | 콘솔에서 재사용 방지가 적용됐는데 페이지가 일반 토큰을 보낸다 → 401 | v3.3.12가 스스로 일회용 토큰으로 바꾼다 |

참고: 06:27에는 429, 10:01에는 401이 났다. 그 사이에 App Check 적용이 켜졌다면 두 증상이 모두 설명되지만, **확인되지 않았다.**

### 1-3. v3.3.12가 하는 일 (방향 C: 토큰 재발급 흐름 개선)

AI 요청이 **401**을 받으면 페이지가 App Check를 스스로 점검한다.

- 일반 토큰과 일회용 토큰을 각각 한 번씩 받아 본다.
- 받아졌는지와 오류 문장만 기록한다. **토큰 값은 화면에도 콘솔에도 남기지 않는다**(점검으로 확인).

점검 결과에 따라 이렇게 처리한다.

| 점검 결과 | 처리 |
|---|---|
| 두 토큰 모두 받아짐 + 일반 토큰을 보냈었음 (H2로 보임) | 일회용 토큰으로 바꿔 **같은 모델로 한 번만** 다시 보낸다. 바꾼 방식은 이 브라우저에 기억한다(`tc_ac_limited`) |
| 토큰 발급 실패 (H1로 보임) | 다시 보내지 않는다. 설정 안내를 띄우고 '자세히'에 App Check 오류 문장을 보여 준다(예: `AppCheck: 403 error. Attempts allowed again after 01d…`) |
| 이미 일회용인데 또 401 | 다시 보내지 않는다. 설정 안내와 점검 결과를 보여 준다(무한 재시도 없음) |
| 401이 아님 | 점검하지 않는다(v3.3.11과 같음) |

'자세히' 예: `HTTP 401 · gemini-3.5-flash-lite · [401 Unauthorized] Firebase App Check token is invalid.` 다음 줄에 `App Check self-check · session token: OK · limited-use token: OK · sent: session`

## 2. 문제 B — 타이핑 딜레이

### 2-1. 측정 (실제 기기 아님 · 비교용)

조건: 헤드리스 Chromium(GPU 없음), 태블릿 흉내(화면 1000×625, 배율 2, 터치), **CPU 6배 감속**, 대화 말풍선 9개.
측정: 0.09초 간격으로 60자를 쳤다. 브라우저의 Event Timing으로 키 이벤트가 화면에 반영되기까지 걸린 시간을 쟀다. 각 2회 측정했다.

| 판 | 키 1개 반영 시간 중간값 / 90% / 최대 | 60자 다 들어가기까지 | 입력창 밖 화면 갱신 |
|---|---|---|---|
| v3.3.11 | 360~368 / 512~584 / 712~776 ms | 27.2~28.9초 | 초당 2.8~3 프레임 |
| v3.3.12 기본 | 24 / 24 / 552~624 ms (최대값은 치기 시작한 첫 키) | 6.2초 | 초당 약 14 프레임 |
| v3.3.12 '움직임 줄이기' | 16 / 24 / 32 ms | 6.0초 | 초당 약 60 프레임 |

(60자 × 0.09초 = 이론상 5.4초)

- **해석:** 이 조건에서는 배경 그리기가 입력 지연의 큰 원인이었다. GPU가 없는 환경이라 실제 기기보다 과장돼 있다. **실제 폰·태블릿에서 확인하지 않았다.**
- 코드상 사실: 페이지는 기기의 '애니메이션 줄이기'(`prefers-reduced-motion`)에만 반응한다. '투명도 및 블러 줄이기' 설정은 페이지 코드가 읽지 않는다.

### 2-2. 바꾼 것

| 위치 | 바꾼 것 | 이유 |
|---|---|---|
| `MOTION`, `MOTION_DEFAULT` (새로 추가) | 움직임 설정. 저장값이 없으면 `'auto'`로 기기의 '애니메이션 줄이기'를 따른다 | 기본값은 결정 대기 |
| `field`(대화 배경) | 마지막 입력 뒤 1.2초 동안은 그리지 않는다. 입력창에 커서가 있으면 초당 약 15번만 그린다. 움직임을 멈출 수 있게 했다(`setStill`) | 입력 처리와 그리기가 부딪히지 않게 |
| `field` (터치 기기만) | 캔버스 배율 상한 2 → 1.5, 작은 호 개수 180~420 → 120~200 | 한 프레임에 그리는 양 줄이기 |
| `sig`(첫 화면 그림) | 로그인 칸에 글을 치는 동안 쉬고, 움직임 설정을 따른다 | 같은 이유 |
| CSS `@media (pointer:coarse)` | 터치 기기에서 말풍선·명령 버튼·입력창의 블러를 끄고 바탕을 진하게 했다 | 움직이는 배경 위 블러는 매 프레임 다시 계산된다 |
| 하단 버튼 `motionBtn` + 문구 2개×6개 언어 | '움직임 줄이기 / 움직임 켜기'. 이 브라우저에 기억(`tc_motion`) | 기기 설정 없이 페이지에서 끄기 |
| 입력창 높이 | 브라우저가 지원하면 CSS `field-sizing:content`로 맞춘다. 미지원이면 예전 방식 | 글자마다 하던 높이 계산(레이아웃) 없애기 |

### 2-3. 진단 테스트 (사용자)

1. 기기 설정 → 접근성 → '애니메이션 줄이기' 켜기 → 페이지 새로고침 → 타이핑해 보기
2. 또는 v3.3.12를 올린 뒤 대화 화면 아래 **'움직임 줄이기'** 버튼을 누르고 타이핑해 보기
3. 버튼을 다시 눌러 움직임이 있는 상태에서도 타이핑해 보기(v3.3.12는 치는 동안 배경을 쉬게 한다)

## 4. 확인한 방법

모두 실제 Google이 아니라 가짜 응답으로 한 점검이다. 페이지의 실제 Firebase 호출 코드를 그대로 쓰고, gstatic의 Firebase 모듈 4개만 가짜로 바꿔 끼웠다. 가짜 모듈은 App Check 토큰 발급과 서버의 재사용 방지도 흉내 낸다.

- **새 점검 28/28 통과**
  - 재사용 방지일 때: 일회용으로 바꿔 1번 다시 보내 답을 받음, 그 방식을 기억함, 다음부터 바로 일회용, 새로고침 뒤에도 유지
  - 인증 실패일 때: 1건만 보내고 설정 안내와 App Check 오류 문장을 보여 줌
  - 일회용인데 또 401일 때: 다시 보내지 않음
  - 정상일 때: 점검하지 않음
  - 토큰 값이 화면·콘솔에 없음
  - 움직임 버튼(멈춤·재개·기억·영어 문구), 타이핑 중 배경 쉼
  - 터치 기기: 블러 없음·배율 1.5, 입력창 높이(field-sizing)
- **v3.3.11 회귀 점검 26/26 통과** (모델 차례 시도, 한도 대기, '자세히' 등)
- 타이핑 측정: 2-1 표

## 5. 사용자가 콘솔에서 확인할 것 (같은 Google 계정)

1. **Firebase 콘솔 → 보안(Security) → App Check → 앱(Apps) 탭**
   - 웹 앱 `good-question-web`이 등록돼 있는가
   - 공급자가 **reCAPTCHA Enterprise(Fraud Defense)**인가(클래식 reCAPTCHA가 아닌지)
   - 들어간 키가 페이지의 사이트 키와 같은가(키 값은 이 문서에 적지 않는다)
2. **같은 화면 → API(APIs) 탭 → Firebase AI Logic 행**
   - 기본 보호가 **적용(Enforced)**인지
   - **재사용 방지(Replay protection)**가 적용인지 → 적용이면 H2 쪽이다
   - 요청 지표(검증됨/검증 안 됨 등)도 함께 본다
3. **Google Cloud 콘솔 → Fraud Defense(reCAPTCHA) → 키**
   - 프로젝트가 `thought-connection`인가
   - 유형이 **웹**인가, 점수 기반(**체크박스 챌린지 끔**)인가
   - 도메인 목록에 **`now4happy.github.io`**가 있는가
   - (Firebase 문서 기준 요건)
4. **v3.3.12를 올린 뒤** 대화를 보내 본다. 안내가 뜨면 '자세히'를 캡처한다.
   - `session token: OK`가 나왔다면 페이지가 일회용으로 바꿔 다시 보냈을 것이다. 첫 인사가 나오면 H2가 맞았던 것이다.
   - `session token: AppCheck: 403 error…`가 나왔다면 1·3번의 설정 문제(H1)다.

| 재사용 방지 | 유지 / 끄기 | 유지하면 요청마다 일회용 토큰(지연 + reCAPTCHA 인증 사용). 끄면 일반 토큰으로 충분하다. 한 번 일회용으로 바뀐 브라우저는 기억값(`tc_ac_limited`)이 남아 계속 일회용을 쓴다(동작은 정상, 비용만 더 듦) |

| 터치 기기 블러 끄기 | 유지 / 되돌리기 | 디자인이 조금 덜 유리 같아진다(스크린샷으로 가독성 확인함) |

- reCAPTCHA 무료(Essentials)는 결제 없이 **월 1만 건(조직 단위)**이다. 넘으면 그달 말까지 429가 난다(reCAPTCHA 요금 문서, 2026-10-26 갱신).
- 일회용 토큰을 쓰면 요청마다 새 인증이 필요하다. 다만 App Check 인증 1회가 reCAPTCHA 평가 몇 건으로 세어지는지는 **공식 문서로 확인하지 못했다.**

|---|---|
| App Check 오류 없이 첫 인사 | 미확인(실제). 가짜 응답으로 H2 경우 통과 |
| 여러 턴 대화 | 미확인(실제) |
| 타이핑 딜레이(움직임 줄이기 켬/끔) | 모의 측정만(2-1). 실제 기기 미확인 |
| 위기 문장 회기 멈춤 / 10번째 보고서 / 종교 인물 인용 | 미확인(실제). 프롬프트·안전 문구 변경 없음 |
| 다른 기기 로그인 | 미확인. 이번 변경과 무관(로그인 코드 변경 없음) |

## 9. 자가 점검

- 안전 문구·주의사항·위기 번호·대화 미저장·개인정보 안내·종교 인물 안내자 표시는 그대로다(기계 대조).
- 비밀: 새 키 없음, 디버그 토큰 없음. 토큰 값은 화면·콘솔에 남기지 않는다(점검).
- 새 문구 2개는 버튼 이름일 뿐이고 가르치는 문장이 없다. 금지어도 없다.
